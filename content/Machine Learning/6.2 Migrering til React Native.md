Migrationen til React Native bød på en række tekniske udfordringer. Først og fremmest skal koden eksekveres på mobilhardware med begrænset batteri og regnekraft. Derudover fylder hvert bibliotek, vi tilføjer, i den endelige app, og for at undgå en bloated telefonapp, er det således også en væsentlig overvejelse at have in mente. Sidst - og nok vigtigst - er der ikke de samme biblioteker til rådighed i React Native som der er i Python - vi mister bekvemmeligheden ved `numpy`, `cv2` og `pytorch`.

Vi skulle med andre ord genimplementere den "lim", der binder preprocessering, inferens og postprocessering sammen. Jeg vil ikke gå ret meget kode igennem - i stedet vil jeg fremhæve et lille stykke kode for at illustrere de udfordringer, vi mødte i dette arbejde, hvordan vi løste dem, og hvilke optimeringsprocesser der stadig ville skulle udføres, før koden ville være produktionsklar.

### Implementering af decoding-logik i TS

Som en del af Python-implementeringen af PaddleOCR-ONNX-modellen, havde vi denne linje kode:

##### Python
```python
preds = np.argmax(probs, axis=-1)
```

som udnytter en NumPy-metode til at tage indekset for den karakter der har højest sandsynlighed for hvert time step, og tilføjer hver af disse i et array, `preds`. Én linje. Logikken håndterer NumPy for os, så vi aldrig behøver overveje præcis hvordan det faktisk bliver gjort. Vores TypeScript-implementering ser noget anderledes ud - her er metoden implementeret manuelt:

##### TypeScript
```typescript

// Antallet af time steps i modellen
const timeSteps = 40;
// Antallet af tegn i vores ordbog
const classCount = 440;

  // Ydre loop: Svarer til at iterere over 'axis=-1' (time steps)
  for (let t = 0; t < timeSteps; t++) {
    // Holder styr på indekset for det mest sandsynlige tegn i time-steppet
    let bestIdx = 0;
    // Holder den tilsvarende score - starter negativt for at kunne arbejde med      negative værdier også
    let bestVal = Number.NEGATIVE_INFINITY;
    
    // Beregn hvor i det flade array, den aktuelle kolonne starter - fordi vi        ikke kan arbejde med matricer, som vi kunne i Python, skal vi manuelt holde      styr på hvor vores 'kolonner' starter, når det ligger i et endimensionelt        array
    const base = t * classCount;

    // Indre loop: Svarer til selve 'max' funktionen
    // Vi checker alle 440 muligheder for at finde det tegn med højest               sandsynlighed
    for (let c = 0; c < classCount; c++) {
      const val = logits[base + c];
      
      // Vi gemmer løbende det højeste index
      if (val > bestVal) {
        bestVal = val;
        bestIdx = c;
      }
    }
    
    // Nu har vi fundet max-indexet for dette time step. Vi gemmer det i arrayet     og ender således med samme array som Numpy-metoden gjorde i Python.
	preds.push(bestIdx);
  }
```

Pointen er, at uden Python bibliotekerne, eksploderer mængden af kode hurtigt. Ovenstående kode er dog ikke den præcise implementering, vi rent faktisk har brugt i vores TS-kode. Fordi vi ikke bruger argmax-metoden, som fylder et array med indekser, kan vi i vores kode i stedet gå direkte til at fylde et array med tegn og et andet med konfidens-scores, uden at skulle gennemløbe et array med indexer forfra - der er således også fordele ved at skrive metoderne manuelt.

Et andet eksempel er skalering af billeder før de sendes til modellen:

##### Python

I vores TS-implementering er det en manuel bilineær skaleringsalgoritme, som jeg lige hurtigt smækkede sammen en morgen (I wish). 
##### TypeScript
```typescript
/**
 * CPU-friendly bilinear resizer that operates directly on BGR packed buffers.
 * We precompute the source coordinate + fractional weights for each axis so the
 * innermost loop becomes a handful of indexed reads and fused multiply-adds.
 */
export function resizeBilinearBgr(
  src: Uint8Array,
  srcWidth: number,
  srcHeight: number,
  dstWidth: number,
  dstHeight: number
): Uint8Array {
  const dst = new Uint8Array(dstWidth * dstHeight * 3);
  if (srcWidth === dstWidth && srcHeight === dstHeight) {
    dst.set(src.subarray(0, dst.length));
    return dst;
  }

  const xMap = createScaleMap(srcWidth, dstWidth);
  const yMap = createScaleMap(srcHeight, dstHeight);
  const srcRowStride = srcWidth * 3;
  const dstRowStride = dstWidth * 3;

  for (let dy = 0; dy < dstHeight; dy++) {
    const y0 = yMap.index0[dy];
    const y1 = yMap.index1[dy];
    const wy = yMap.weight[dy];
    const wyInv = 1 - wy;
    const topRowOffset = y0 * srcRowStride;
    const bottomRowOffset = y1 * srcRowStride;
    const dstRowOffset = dy * dstRowStride;

    for (let dx = 0; dx < dstWidth; dx++) {
      const x0 = xMap.index0[dx];
      const x1 = xMap.index1[dx];
      const wx = xMap.weight[dx];
      const wxInv = 1 - wx;

      const dstIdx = dstRowOffset + dx * 3;
      const topLeft = topRowOffset + x0 * 3;
      const topRight = topRowOffset + x1 * 3;
      const bottomLeft = bottomRowOffset + x0 * 3;
      const bottomRight = bottomRowOffset + x1 * 3;

      for (let c = 0; c < 3; c++) {
        const top = src[topLeft + c] * wxInv + src[topRight + c] * wx;
        const bottom = src[bottomLeft + c] * wxInv + src[bottomRight + c] * wx;
        const value = top * wyInv + bottom * wy;
        dst[dstIdx + c] =
          value <= 0 ? 0 : value >= 255 ? 255 : (value + 0.5) | 0;
      }
    }
  }

  return dst;
}
```

### React Native-kompatible biblioteker
Nogle af vores TS-implementeringer kan også implementeres gennem diverse biblioteker i stedet for manuelle implementeringer - hvilket vi også har gjort i nogle tilfælde med f.eks. Skia-biblioteket fra Shopify. Det er dog ikke nødvendigvis altid en helt nem afvejning, hvad der giver bedst mening.

**Bloat og dependencies**
Én overvejelse er, at app-størrelsen bliver forøget hver eneste gang vi importerer et nyt bibliotek - og mange biblioteker har deres egne afhængigheder, så der kan pludseligt opstå en masse bloat. Er det f.eks. det værd, hvis man har en enkelt metode, som et eksternt bibliotek har en superoptimeret løsning på, men som så tilføjer 10 mb til appstørrelsen og øger indlæsningstiden af appen? Det kommer selvfølgelig an på den konkrete metode, men som oftest er svaret nok nej. Har man derimod 50 metoder fordelt i sin kodebase, der kunne have gavn af det samme bibliotek, er det måske det værd. Det vil altid være en afvejning.

**Data-format & Overhead** 
Manuelle implementeringer har også den fordel, at de kan tilpasses præcist til vores konkrete use case, og vil derfor faktisk i nogle tilfælde præstere bedre end biblioteks-metoder. Derudover har de modeller vi bruger, nogle helt bestemte karakteristika i hvilke formater de tager som input og producerer som output. Mange biblioteker til React Native, såsom Skia, er optimeret til grafik (GPU) og arbejder i `RGBA`-format. Vores ONNX-modeller kræver data i `BGR`-format på CPU'en. Hvis vi brugte et grafik-bibliotek, ville vi spilde dyrebar tid på at flytte data frem og tilbage mellem GPU og CPU samt konvertere formater.

**Python vs JS**
En slagside ved at bruge manuelle implementeringer er dog, at JavaScript ikke er lavet til komplicerede matematiske operationer. Tager vi f.eks. NumPy-biblioteket i Python, er koden her enormt optimeret - det kan vi aldrig matche med JS-kode, men det er heller ikke altid nødvendigt. Tung pixel-aritmetik er 'dyrt' i JS, og der er således en vigtig performance-afvejning her, som bl.a. kommer an på størrelsen af et givent billede.
