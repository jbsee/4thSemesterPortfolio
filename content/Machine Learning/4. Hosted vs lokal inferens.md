Vores projekt er bygget op omkring at skulle lave en mobilapp. Det sætter rammer for både ydeevne, sprog/runtime og brugeroplevelse. Nedenfor skitseres praktiske konsekvenser for to arkitekturer: lokal inferens på telefonen og hosted inferens på en server.

### Mobil inferens

- **iOS og Python** iOS tillader ikke dynamisk kodeeksekvering. Kode skal være kompileret og en del af appens binære pakke, ikke fortolket ved kørsel. Python fungerer på dette område grundlæggende anderledes end f.eks. C#: det er en fortolkende runtime, der ikke kompilerer koden til maskinkode, men eksekverer koden ved kørsel. Dette regnes som dynamisk eksekvering og falder derfor uden for de krav, iOS stiller til kompileret kode.

> **Fortolkning, sikkerhed og platformspolitik**  
> iOS begrænser dynamisk kode hovedsageligt af sikkerhedshensyn og kontrol. Apple vil vide præcis, hvad appen kan udføre, før den installeres, og tillader derfor ikke runtimes, der kan eksekvere ny eller ændret kode efter installation.
> 
> **Python (fortolkende runtime)**
> Embeddet Python kan både fortolke ny kode og loade scripts ved kørsel og samtidig få adgang til systemniveau gennem native bindings. Det betyder, at koden i princippet kan ændre sin funktionalitet efter installation og udføre systemkald direkte.
> 
> **JavaScript (sandkasse)** 
> JavaScript kører dynamisk, men i React Native holdes det i et sandkassemiljø med glasvægge: det kan regne, manipulere data og styre UI, men det kan ikke selv opbygge nye native bindings eller få direkte adgang til kamera, GPU eller filsystem. Al systemadgang sker kun gennem på forhånd kompilerede og godkendte moduler, som ikke kan udvides ved runtime.
> 
> **C# (kompileret)** 
> C# oversættes til maskinkode før upload til App Store. Koden ligger statisk i appens binære pakke, kan ikke ændres af appen selv og opfører sig deterministisk i runtime.  
> Derfor tillader iOS C# og kontrolleret JavaScript, men ikke en Python-runtime, der kan fortolke og eksekvere kode ved kørsel.

I et React Native-setup er det derfor ikke en realistisk løsning.

- **Android og Python** 
  Det er muligt at embedde Python, men det er komplekst i et React Native-miljø: separat runtime, opstartstid, større APK/Bundle, native bindings, edge-cases i livscyklus. Vedligehold bøvler og performance bliver uforudsigelig.

- **Migrering til JS/TS (React Native)** 
  En anden mulighed for lokal inferens er at migrere Python-koden til React Native/TS. Dette medfører dog, at man mister adgang til en række Python-biblioteker (fx OpenCV), som er stærkt optimeret i C/C++ og udnytter hardware-acceleration. I React Native kan disse funktioner ikke bruges direkte, og man skal derfor enten finde tilsvarende biblioteker, der fungerer på tværs af mobilplatforme – eller skrive sine egne JS/TS-implementeringer af de specifikke pre-/post-processing-opgaver, man har brug for. Det giver større kontrol, men også øget kompleksitet og sandsynligvis lavere performance. En fordel er dog, at .pt-modeller kan eksporteres til ONNX-format, som kan eksekveres direkte på telefoner via ONNX Runtime Mobile.


### Hosted inferens

**Styrker**
- Hurtig vej til drift: hele Python-økosystemet er tilgængeligt på serveren.
- Potentielt kraftigere hardware - gevinsten er dog afhængig af en stabil og hurtig netværksforbindelse.


**Svagheder**
- Udgifter: Alt efter inferenskrav kan det være nødvendigt med en relativt kraftfuld server.
- Latenstid: Når dataen skal sendes frem og tilbage mellem klient og server medfører det ventetid.
- Forbindelsesrisiko: dårlig dækning = langsom eller ingen funktion.

### Lokal inferens

**Styrker**
- Lav latenstid: intet behov for at kommunikere med server.
- Offline-funktionalitet.
- Ingen serverregning pr. inferens.


**Svagheder**
- Portering: kode skal migreres til React Native kompatibelt JS/TS.
- Hardwarebegrænsninger: Hardware begrænser modelstørrelse og throughput og bruger batteri.
- Opdatering: nye modeller kræver app-opdatering.

### CIA-triaden

- **Confidentiality** 
  Uanset løsning vil data før eller siden sendes til en server, hvis den skal registreres eller lagres. Lokal inferens reducerer dog mængden af data, der sendes, da selve billedbehandlingen kan ske på enheden. Ved hosted inferens kræves altid kryptering og dataminimering.

- **Integrity** 
  Handler om at data og modeller ikke ændres utilsigtet. Ved lokal inferens er der ikke risiko for ændringer under transport, fordi data behandles på enheden. Ved hosted inferens sendes data over netværk og har derfor større angrebsflade, men til gengæld kan serveren dokumentere, logge og kontrollere modelversioner.

- **Availability** 
  Lokal kørsel fungerer uden net. Hosted er afhængig af dækning og backend-oppetid. Caching/queueing kan afbøde, men løser ikke total udfald.


### Telefoner og performance

Målgruppen er telefoner fra omkring 2020 og nyere (f.eks. IPhone 12, Google Pixel 5). Disse telefoners hardware burde være godt nok til en lokal ML-pipeline som vores, når modellerne er kompakte og kvantiserede. Det er således et spørgsmål om hvor mange sekunder der er acceptabelt for at køre pipelinen, hvilket kan justeres med størrelsen af modeller og optimering af pre-/postprocessing af billeder.

### Konklusion og vores valg

Ønsket om offline-funktionalitet og en forventning om, at telefonerne kan bære pipelinen, har ledt os til at forsøge med **lokal inferens**. Derfor har vi besluttet af forsøge os med at migrere Python-prototypen til **React Native + TypeScript** med ONNX Runtime Mobile til at stå for selve eksekveringen af modeller. Hosted inferens er fortsat et reelt alternativ, hvis der opstår behov for tungere modeller eller hvis det skulle vise sig af den ene eller anden grund ikke at være holdbart med den lokale løsning.
